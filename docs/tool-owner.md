# Canonical tools owner

`server/tools` is an additive portable owner, **shared by the host composition and Live acceptance**. It implements the accepted model journal and result gate without changing their signatures. It uses the existing Store and MCP registry/adapter, and the accepted Lux knowledge reader. Its typed `tools` version-1 migration adds `tool_connections`, `tool_runs`, and `tool_calls`. Version 2 adds the immutable `tool_connection_semantics` discriminator table without rewriting legacy policies. There is no Chat foreign key, second database, refusal table or independent authorization registry.

## Trusted composition

Supply `toolsMigrations` when opening the existing Store, then construct one `createToolsOwner` for that Store object lifetime. Store acquires the exclusive `writer.sqlite` lock before tools initialization. Owner construction atomically seals only its own pending intents `unknown`, once. It does not replay, retry, rekey, recover another owner's rows, or use the persistent authority epoch as a process-start identifier. A second owner on the same Store object is rejected, even with a different owner ID. Host composition constructs this owner once; never create a replacement owner over a live Store.

The trusted `lookupAuthority(runId, signal)` returns live owner/actor/run/epoch/revision, the exact provider/model route, permitted classes, connection IDs, and the accepted run hash (or null). It must read application authority, not echo HostContext, connection configuration, or model input. Host grants are not this owner's permission source.

`applyConnection` takes a strict explicit `ConnectionPolicy`. No defaults: IDs, schemaVersion, enabled flag, endpoint URL/account/resource/credential reference, read-only names, approved schema digest/generation, source policy ID/revision/unknown class/allowset, route identity/allowset and positive safe-integer query/get/entity/result budgets are required. Identical canonical policy bytes are a SQL no-op; changed bytes strictly advance generation. Connection identity and endpoint ID cannot change or be deleted. SQL guards also prevent INSERT OR REPLACE from bypassing retained identity. Endpoints cannot be reused by another connection for this owner.

Policy changes commit **before** projecting suspend/revoke into the existing MCP registry. A projection error cannot undo revocation. Egress enabling and reviewed discovery are separate trusted setup. `projectConnection` approves only persisted enabled policy against matching endpoint configuration and reviewed discovery. It cannot roll a live registry back to a prior generation or reapprove a suspended generation. A newly composed registry after reopen may project persisted enabled approval; disabled policies cannot resurrect it. There is no DB/network atomicity claim. MCP's existing final transport grant reread covers credential-await suspension, not the future model transport boundary.

`snapshotRun(tx, acceptance)` participates in the supplied existing synchronous transaction. It stores immutable acceptance and every bound policy's generation, digest and exact canonical bytes, and returns the accepted hash for application authority. Identical acceptance is idempotent; differing acceptance collides. No network or awaited authority lookup occurs in the transaction. Every run update/delete and call identity/intent/argument modification is forbidden by SQL triggers. Only pending intent-to-terminal transitions are permitted; terminal bytes never change.

`definitions(runId)` produces strict `additionalProperties:false` declarations for `search_knowledge({query,limit})` and `get_insight({ids})`, limited to approved names. It binds account/resource/policy/route outside arguments. Multiple connections with colliding tool names are rejected; future name routing is not silently invented. Selected-note recall stays separate.

## Execution and continuation

The accepted loop commits journal intent before executor dispatch. Duplicate exact intent returns existing and stops uncertain; a collision throws, without creating a replacement refusal or invoking the tool again. Targetless refusal can create a terminal record only for a fresh identity. Call IDs are retained uniquely within an owner/run, including across execution keys.

Executors validate exact committed identity/arguments/scope, await live authoritative lookup, and reread the selected connection policy synchronously before calling the accepted reader. The reader forwards the signal to actual MCP dispatch. Abort before dispatch causes zero calls; abort after potentially remote completion remains unknown. Unknown completion cannot be overwritten later. Terminal snapshots contain detached model-visible JSON, intent binding hash, result ID and exact UTF8-byte SHA256 in one atomic transaction. There are no remote calls inside SQLite transactions. A failed result write is latched for that execution so the loop cannot manufacture a replacement failed receipt and continue. The latch only denies fallback writes; it is not another authorization authority.

Before **every** provider request, including initial requests and runs with no connections or no result references, the result gate verifies authoritative scope, accepted hash, exact route/classes, the current enabled policy and registry projection for each result being released. The persisted-policy reread occurs after awaited lookup, catching revocation during the await. It validates each exact result reference/hash and stored execution/name/call/arguments binding. Unknown/pending, foreign, missing, corrupt or disallowed results deny the whole request. Returned response objects are detached copies. The accepted loop retains coverage/order and response matching checks; this owner does not replace them. Gate/storage failure stops the next provider request rather than stripping evidence and continuing.

## Lux evidence coverage

The actual Lux reader and MCP adapter are used, not a direct raw-result path. The owner reads slices of at most 512 bytes, verifies complete entity length/hash/expiry and endpoint URL/account/resource/schema/generation/tool scope, decodes strict UTF8 and supports only a JSON-RPC 2.0 text-only MCP result envelope. Oversize, incomplete, expired, missing, capacity, protocol, unsupported envelope and transport errors are not empty successes. Empty valid `content:[]` is a distinct successful empty text snapshot. No upstream text is silently truncated into complete evidence. Only bounded projected text and provenance persist; the ephemeral HTTP archive/handle and credentials do not enter durable tool receipts or provider context.

The reader's `unknown` and `local-only` labels are unconditional conservative defaults, **not source-supplied prohibitions**. Explicit trusted `unknownClass` plus source/route/actor consent may create a separate classified snapshot without mutating raw reader evidence. Missing unknown policy is an invalid DTO; `unknownClass:null` denies. No markdown classification inference occurs. `projectLuxResult` additionally accepts separate trusted typed restrictions: actual local-only/non-disclosure denies, and known classes must remain allowed and are retained. The current reader does not parse arbitrary typed restriction metadata. The supported envelope rejects additional result/content forms without claiming semantic enforcement of arbitrary source metadata. Application wiring for trustworthy typed metadata is not delivered here.

Provenance preserves unknown source version, observation time, original entity integrity hash and single-tool-result coverage, with `completeCorpus:false` and remote side effects unverified. Get `requestedIds` are explicitly unverified caller input, never verified returned entities. This is not full-transcript coverage. Root-approved real endpoint/source/account policy is future configuration.

## Runtime composition (W-C)

`server/host/runtime.ts` constructs one `composeMcpRuntime` at startup on the already-open Store. It builds a single registry, adapter and `createToolsOwner`, discovers every configured endpoint (bounded, never blocking startup), and returns a `LiveToolsComposition` shape `{ owner, connectionIds() }`. `connectionIds()` returns the ids of the configured, enabled, egress-allowed endpoints at call time. The composition is passed to `composeLive` as the trailing argument and exposed on the host result as `tools`; a missing or unreachable endpoint yields a typed error state and a refused connector call, never fabricated empty data. The grant evaluator is unchanged: discovery alone never grants authority.

### Explicit voice remembering

Live sessions declare the gateway-owned `remember_note` tool with `text` (1 to 500 characters) and `kind` (`fact`, `preference`, or `task`), and no other arguments. It executes locally, not over MCP. The **owner-trusted explicit voice memory rule** permits only this built-in write identity in `owner-trusted-reads`; explicit grant mode leaves it unapproved, and a remote MCP tool with the same name receives none of its permission. Other writes remain unapproved. Original argument validation, owner authority checks, intent journaling, result authorization and result journaling still apply.

The gateway saves the owner's finalized input transcription, not the model's proposed note. The latest finalized explicit remember command in a bounded 64-fragment journal window supplies the payload. The model text must match that payload after case, whitespace and terminal-punctuation normalization, or be a normalized substring of it. A missing finalized command refuses with `owner_transcript_not_final`; a mismatch refuses with `owner_text_mismatch`. One finalized utterance can produce only one entry; a repeat refuses with `already_remembered` and identifies the existing entry. Provenance identifies `live-voice`, the Live session id and the finalized utterance journal sequence. The entry's existing source-reference note retains `kind:<kind>` without changing its owner-authored content.

Voice remembering writes **ordinary memory only**. An explicit request to classify the note as private or sensitive refuses with `private_memory_unsupported`; it is never silently downgraded. Private notes must use an owner-controlled workflow, not this voice tool. Live-voice entries have **no deletion control yet**. Durable memory deletion is deferred to a separate wagon, not available through the Live projection or the selected-memory picker.

A successful result is only `{remembered: true, entryId}`; refusals return `{remembered: false, code}` (duplicate refusals additionally identify the existing entry). Note text is never echoed in the tool result. Naya confirms aloud only after success and otherwise reports the refusal. Saving does not modify the running session's `accepted_prompt_snapshot` or `prompt_identity`: recall occurs at the next session CREATE.

### Host-confirmed composed notes (C-LUXWRITE, W6)

`stage_lux_note` is declared to the live model only while `live.json` carries
`"features": {"composedNotes": true}`; the shipped default is off. It takes `title` (1 to 120
characters), `body` (1 to 2000), and one to eight `evidenceRefs`, which must name journal rows the
session holds. It stages; it never writes.

Authorization is the owner's own finalized microphone turn (`final_origin` not `typed`) and an
anchored grammar: an imperative save, remember, put, add, write or store verb plus an explicit lux
destination. A negated, reported, quoted, conditional or hedged form is a clarification; an append,
update, delete, link, archive or restore ask is answered as unsupported and never becomes a create.

The host freezes the whole `save_insight` payload and its sha256 at stage time. Nothing is truncated:
an oversized title plus body is refused whole. Confirmation is armed only by the app's own
`playback.drained` receipt for the read-back segment; `interrupted` or `terminated` invalidates the
stage. The next finalized owner turn inside 30 seconds decides on an exact affirmative allowlist (at
most six tokens, closed disqualifier set), and a 1.5 second settle window cancels on any further
owner fragment, so a VAD-split "yes ... wait, make it fifty" never commits. The commit claims one
`vault_writes` row keyed by the stage, so a second settlement inserts nothing, and it dispatches once:
no retry, unknown stays unknown, saved only on `inserted`. `save_to_vault` keeps its dictation span
check, so a generated summary cannot ride the save phrase.

### Notes exporter (C-LUXWRITE item 12)

At session end the host flushes `remember_note` entries of kind `fact` or `preference` through the
same lux client: one row per note, project `didi-voice`, `USER_PREFERENCE` for preferences and
`UNCATEGORIZED` otherwise, provenance in the body, six words of context in no row. Dedupe is a
normalised key checked locally and against lux (`search_knowledge`, a read); a word overlap above
0.95 skips the row. Ten rows per flush, twenty per rolling day, never session gists, tasks, imported
history or the owner profile. The ledger row is written before the call, so a crash leaves an attempt
with an unknown outcome and never a replay. The switch is `"features": {"notesExport": false}` to turn
it off; the shipped default is on. The log event carries counts only.

### What a memory recall reads

A memory lookup reads earlier conversations only: remembered notes, summaries and retained conversation rows from before the call in progress. It never reads the live session's own transcript, her own summary of it, or the owner's current question, so an answer can never be proved by the question that asked it. Within what it reads, every matching line is evidence: the line with more matching words leads, and at the same match a summary leads an entry leads a live transcript line, newest first among equals, so a match on an owner line never narrows the recall to her own earlier questions; the one exception is a question about what she said, where her own words are the answer. When nothing from an earlier conversation matches, the source reports itself empty instead of falling back to this turn.


## The Trello board (W7)

The owner granted Naya full read and write on his one Trello board (owner ruling 2026-10-25): single turn, no spoken confirmation, archive allowed; never another board, never creating boards or creating or moving lists, never member changes, never a delete (the server has none). The owner's Inbox is read, and one of its notes can be moved onto a list of the board (W7-R1); no other Inbox write, and no Planner, is ever offered. The Live model is declared two gateway tools, `trello_read` and `trello_write` (`accountId gateway:live-voice`, `resourceId owner-trello`), only while a Trello sign-in record exists and only under `owner-trusted-reads`; text chat never sees them. Each call is journaled like `remember_note`: intent first, then the board service, then one terminal receipt.

The board service (`server/tools/trello.ts`) holds the rules:

- **Board pin.** The board name is the owner's private configuration, never this repository (W7-R2): `trello-board.json` beside the sign-in record, `{"board": "<the name he sees in Trello>"}`, read at connect. With no name the connector reports `not_configured` and nothing reaches the server; with a name, the first call of a session lists the boards of the signed-in workspace through the server and keeps the one open board whose name equals it after folding; none is `board_not_found`, two are `board_ambiguous`. Lists, labels and open cards are read from that board only and cached for 60 seconds per session.
- **Resolution before dispatch.** A list is named by its folded name (case, spacing, `&` against `and`); an unknown or ambiguous name is `list_unknown` or `list_ambiguous` with the closest list names, never a guess. A card is a session handle (`C3`) from an earlier result, its folded name, or an ARI that the server confirms lies in a pinned list; anything else is `outside_scope`. No argument names a board.
- **Server surface.** Only these server tools and actions can be called: `trelloReadMember get_me`; `trelloReadBoard list, list_labels`; `trelloReadList list_by_board`; `trelloReadCard get, list_by_list, list_comments`; `trelloReadChecklist list_by_card`; `trelloWriteCard create, update, move, archive` and the label actions; `trelloWriteChecklist create, add_item, create_item, update_item`. `trelloWriteBoard`, `trelloWriteList`, Inbox, Planner and member tools are never called, and the client refuses them before any network. The server publishes its tool names but not its input schemas, so every call is planned against the schema the server advertises in `tools/list`: a call whose action or fields the schema does not accept is `unsupported`, never sent in a guessed shape.
- **No comment tool.** The server carries no comment action, so `note` appends one dated line (`YYYY-MM-DD: words`) to the card description and the receipt's `change` says the note was added to the description (W7-R5). A note that would pass Trello's description ceiling is `description_full` and is not added.
- **Reads.** `overview` (every list, true card count, newest three), `list` (paged with the true `total` and `nextOffset`), `search` (name and description, on the pinned board, never server search), `due` (overdue first, then today or the week, in the host time zone, with `datedCards`), `card` (with checklists; comments only if the server offers `list_comments`, which it does not yet), `recent` (cards created today, from the creation time in the card id). Trello Inbox, where its phone quick capture lands, is out of reach by the owner ruling.
- **Writes.** `create`, `update`, `note` (a dated line appended to the description, because the server has no comment tool yet), `checklist`, `due` (local `YYYY-MM-DD`, `YYYY-MM-DDTHH:MM` or `none`; 09:00 when no time), `move`, `done` (to the list named Done, or due complete when there is none), `label`, `archive`. A write needs a change cue in the owner's own words of that turn (`not_owner_requested` otherwise). Each resolved write is keyed by session, action and resolved arguments: a confirmed or unknown key answers from its first receipt with `replayed: true` and is never sent again; a definite refusal changed nothing and may be asked again. Nothing retries. A reply with no card is read back once to build the receipt; the receipt carries `change`, the only thing Naya says changed.
- **Log.** One content-free `connector_call` line per phase (`admit`, `dispatch`, `settle`) with the tool, outcome and closed reason ([debugging.md](debugging.md)).

The tool descriptions are voice content and are pinned by `server/test/trello-guidance.test.ts` in `check-prompt.sh`; the board, its sign-in and the asks of the contract as rule-judged rows run in `check-company-connectors.sh` against `server/test/trello-fake.ts`, and the Live wiring runs in `live-remember.test.ts`.

## Text chat consumption

Text chat consumes the canonical owner and the host's existing connection
selection; it does not create another evaluator, journal, result gate or schema
derivation. A frozen conversation acceptance limits which original read
declarations can be supplied. Every actual dispatch remains subject to live
owner authorization and registry revocation. The acceptance binds the provider,
model, route, permitted classes and connection policy identity, and cannot be
reused after those route inputs change. New approvals require a new conversation.

The shared model tool loop has a four-request bound in chat. Every provider
request, including an evidence follow-up, requires current conversation consent.
The model sees only the result gate's accepted projection; browser cards are
bounded markdown and permitted sources from that same boundary, not raw MCP
content or tool_calls JSON. Chat reuses the canonical gate at the finite loop
boundary before projecting the last accepted results. Denial remains denial,
never a connector-specific fallback or authority synthesized from model output.

## Connection-scoped admission (T8-FIX, council option B)

Acceptance freezes the admitted connection ID set and the route's explicit allowed-class set. Host IDs are the intersection of owner-approved local connections and usable current grants, not every endpoint with a healthy handshake. Discovery can make a connection available to a later run, but never adds it to an existing snapshot. Each execution selects only its own bound connection: unrelated connections cannot poison an otherwise authorized read. Connection policy `route.identity` is retained for legacy/audit compatibility; it is not a model-route approval and is never compared with the run route identity.

Before MCP dispatch and again before result release, the owner checks admitted membership, live authority, current approval generation/hash, local READ classification, original-schema validation and approval binding, connector restrictions, source class and result scope/freshness. Source class must be a member of each explicit applicable class set, including the run route's set; there is no ordinal class hierarchy at either gate. The bounded local `unknownClass` supplies the source classification when no approved local tool/source classification is more specific. Intent and terminal result JSON both journal the run's `routeIdentity`; terminal hashes bind it to the original intent.

New explicit owner approval adopts `bindingMode: 'connection'` and records that semantic discriminator in the version-2 table. Migration alone grants no authority to legacy rows, even if their route identity equals an endpoint ID. Host reconciliation may adopt unambiguous endpoint-bound legacy rows only from explicit bounded local configuration under the existing owner-trusted-read approval; ambiguous legacy routes fail closed. Null/absent classifications cannot become executable connection approvals. There is no wildcard route identity.

Startup preserves persisted approval fields, bounds and revocations. It compares canonical security-relevant content and uses owner CAS only when it changes; unchanged restarts do not bump generation. Newly discovered tool names, endpoint changes or classification lowering require explicit owner approval. Classification tightening and removal of previously approved tools apply immediately. Classification ordering is used only to distinguish a tightening config change from a lowering, never to authorize data release.

T8-FIX-R1 invariant coverage uses real host composition with fake connector/model transports: the actual Live acceptance builder, and the public `snapshotRun` API with chat-style route identity. W-U owns the later real ChatService extension. R4 admits this integration file to the canonical compiler; no ChatService composition is fabricated here.

## Rich, clean Live tool results

`server/tools/live-shape.ts` is the single shaping seam for the text a connector result puts in front of the model. It is pure and deterministic: `renderGoogleTool` (Gmail/Calendar), `renderMattermostTool` and `projectLuxResult` delegate to it, so Live and Chat read the same `response.text`; the full raw wire result is still retained in the MCP payload/entity store, so nothing is lost. Gmail bodies are HTML-converted and stripped of quoted chains, signatures, MIME boilerplate, inline base64 and tracking URLs while keeping sender, recipients, date, subject, labels and attachment names; Gmail lists keep sender, date, subject, snippet, unread flag and thread size, and each list entry also carries out of band whether it is bulk mail (a list header or a machine sender) and whether the owner wrote it, so a triage read can rank a person's question above a newsletter before its line cap. Mattermost keeps full text, author, channel, timestamp, reaction count and thread position, and drops system join/leave posts. Calendar events keep time, title, location, attendees, organizer, description and conferencing presence; the attendee and organizer lines are never cut (the attendee line gives the true head count, up to eight whole names and `and N more`, or `at least N people ... and others` when the helper truncated its own list), only the description is cut against the per-event bound, and no line carries a character count. Lux knowledge search keeps title, type, date, id and a substantial excerpt, and `get_insight` return bodies.

Named per-tool bounds (`GMAIL_BODY_CHARS`, `GMAIL_LIST_MESSAGES`, `CALENDAR_EVENTS`, `MATTERMOST_MESSAGE_CHARS`, `MATTERMOST_MESSAGES`, `KNOWLEDGE_EXCERPT_CHARS`, `KNOWLEDGE_HITS`) are generous, and the list bounds equal the largest slice the connector can fetch, so a list is never cut. When a bound does cut, the text says so explicitly and never mid-sentence: a lux search hit names `search_knowledge`'s real `limit` follow-up, a lux excerpt names `get_insight` with the hit id, and a single message or post cut is reported as final because those tools have no partial re-read argument (W7-R2).

Warm connectors: one `McpAdapter` is composed per host runtime (`server/host/mcp.ts`), and its `sessions` map (`server/adapters/mcp/adapter.ts`) returns the existing stdio child for every later call, restarting only after the child closes or a call fails. There is no pool and no hedging. Batch dispatch inside one provider batch is concurrent in `server/tools/declarations.ts`; same-endpoint calls run concurrently up to the adapter's per-endpoint limit (default 6) and queue beyond it, so a provider batch reaches different endpoints and one endpoint at once through one combined `toolResponse`.

## Opening things

The open tools (`server/tools/open.ts`) only open: `open_source` takes a handle, `open_home` one of three home pages, `open_file` a home-folder path and `open_app` an application name. No model argument is ever a URL. A handle is minted only in `server/tools/open-handles.ts`, from a structured connector record of this session, and opens only once its `open:` line reached the model (exposure) and only when the owner's own words carry an open verb and a matching kind.

- Destinations: https, no userinfo or port, never a `url`, `redirect`, `export` or `download` path and never a `q`, `redirect` or `export` parameter. Gmail is `mail.google.com/mail/u/<index or account address>/`; Calendar is `calendar.google.com/` or `/(calendar/)event?eid=` there, plus the link the Calendar API really returns, `www.google.com/calendar/event?eid=` (path exactly `/calendar/event`, nothing else on that host); Docs, Sheets and Slides are `docs.google.com/<document|spreadsheets|presentation>/d/<id>`; Drive files are `drive.google.com/file/d/<id>/view` (Office files and PDFs open in that viewer) and folders. The native list in `Sources/LuxDidi/NativeActions.swift` is the same list: `server/test/fixtures/open-destinations.json` is one table both run (`check-tool-owner` for the host, `check-native-live` for the native side), and a parity test compares the host names of both sources.
- Gmail: a message or thread opens at `https://mail.google.com/mail/u/<account>/#all/<threadId>` (all mail, so an archived thread opens too). The account is the address the Gmail endpoint proved at host start with its own `gmail_get_profile` (`noteGmailAccount` in `server/host/mcp.ts`); with no proven account the link uses `/u/0` and `host.log` gets one `gmail_account_unknown` per session. A link inside a mail body is someone else's text and never mints a handle; the read message itself does.
- Drive: research source `drive` reads the lux-cli Drive family. A name search (`drive_search_files`, the kind he named as a type filter, at most five newest first) that finds one file mints its handle from `webViewLink` only; several plausible files mint nothing and the result asks him to choose (`DRIVE_CHOOSE_GUIDANCE` in `server/tools/live-shape.ts`); his pick is read again with a lookup query `id:<file id>`, and that fresh `drive_get_file` result is what mints. `webContentLink`, `exportLinks` and download links are never read. With no Drive endpoint the lookup is `drive_not_available`.
- Evals: `server/test/fixtures/open-evals.json` holds the rule-judged open rows E1 to E10 (synthetic setups, judged on the open argument and its resolved target). `open-destinations.test.ts` replays E1 to E9 host side with the model step scripted; E10 is the owner's manual proof that Chrome shows the expected page.

The native side opens a web destination in Chrome when it is installed and in the default browser otherwise ([native-app.md](native-app.md)).

## Public web evidence

Public queries use Gemini `gemini-3.8-flash` with `google_search`, low thinking, one candidate and a 1,100 output-token ceiling. The synthesis is at most 220 words with up to five cited sources. The single total deadline is 8 seconds for every web ask, the same number the research source row reads: the web reads that succeeded on this host took 3.3 to 4.4 seconds and the retry shares that budget. A cut read is said as the web taking too long, never as an outage. An empty, ungrounded or cap-emptied result gets one broader query retry within that same deadline. No private connector context is sent.

`web_insufficient` carries the typed reason `empty`, `ungrounded`, `capped` or `reply_budget`. A success must retain at least one supported claim and source after the word cap. Reply compaction retains whole supported sentences and the first source line, and tells the model it may ask for the full result; evidence that cannot fit is insufficient, never a successful empty finding. Citation URLs and attribution have a separate 12,000 character metadata budget outside the 2,500 character spoken reply. Early replies are capped again after the pending envelope is attached and preserve the more-available sentence.

Fallback public-fact routing includes prices, versions, public names, dates, population, exchange rates and scores. Questions naming mail, calendar, chat, our, my or we never acquire web from that fallback. Explicit routed web reads are unchanged. Query bounds remove filler words before retaining whole entity, date and place tokens.

## Chat routing and its own read budget (#635, #645, #646)

A chat read runs only when the ask needs it. The chat surface words (`chat`, `channel`, `mattermost`, `slack`, `dm`, and a message from a named person) route it on their own; a writing verb (write, draft, summarise, compose, reply) or a pure recall ask (what did I say, remind me, what did we discuss) leaves a chat word as the ask's subject, so the ask reads her memory and no chat leg runs. Every chat search asks the archive for keyword mode, never the embedding modes that took tens of seconds per read, and a keyword search that matches nothing on every word earns one retry with its single most specific word, which the answer names as a broadened match. The chat read has its own 10 second row in the per-source deadline table, inside the research turn and under the 12 second connector timeout: above the 5 to 12 seconds a real read takes and above the 4.5 second session release, so a cut is the exception. A chat read that runs past it returns what arrived, marked `partial_timeout`, or `timed_out` when nothing arrived, and the voice says the read took too long, never that the chat could not be reached.

The chat read is picked by the ask's shape (`server/tools/chat-intent.ts`), never by a channel regex or a person's name used as a keyword (C-CHAT). What a person wrote him reads that person's posts in their direct messages, and "my chat with" a person both sides; what he discussed with a person is the overview across their direct messages, shared group chats and channels where both posted, with counts; a named channel reads that channel; a group chat with some people reads the group whose members are exactly those people; anything else stays one keyword search over every channel. The person, group and channel reads go through the connector's own composite `mattermost_chat`, which resolves the spoken name strictly (case, accents, `&` and `and`, a plural and its singular are one name) and asks back when it fits several (`Ask him: Which Lena do you mean ...`, coverage `chat needs_clarification`), never a guess; a person or group nobody has is `name_not_found`, an unknown channel the closed `channel_not_found`. The window looks backwards in the owner's zone with both ends sent (`last week` is Monday to Sunday), and a future window (`next week`, `tomorrow`) reaches no chat read. The reply note says what was read and over which days (`I read direct messages from ... since ...`), the header carries the archive's own match count (`chat truncated_to_budget 8 of 71 shown`), and a continue on that run reads the next page by offset, one page per call. The attention read takes the direct and group conversations that moved by their last post and windows its own searches, newest first, in keyword mode. A child without a capability keeps the best read it has and the note says once which capability is missing ([connectors.md](connectors.md)).

## Research coverage header and one-turn escalation (#621)

Every `research` reply opens with a `coverage` string, before the findings: `coverage: `<source> <status> <shown> of <matched> shown; ...` for each source it searched, and `<source> <reason> (say: <clause>)` for each source the ask routed to but nobody read. Searched status is one of `complete`, `partial_timeout`, `truncated_to_budget`, `empty_after_retry` or `partial_failed` (a read whose later page failed after one page arrived is never `complete`, whatever the counts add up to); an unsearched reason is one of `not_connected`, `not_configured`, `grant_missing`, `provider_failed`, `skipped_by_route`, `timed_out`, `still_reading` or `never_ran` (#635: a read cut at its own budget with nothing arrived is `timed_out`, never `provider_failed`, and a read still in flight when the reply is composed is `still_reading`, the same thing the note says; L8-13: a continue whose source deadline was already spent dispatches no page and is `never_ran`, never `partial_timeout` and never "took too long"). The counts are rederived from the findings the voice actually receives, so a trim can never make them disagree with the evidence. The header counts inside the 2,500 character reply envelope, at most a quarter of it, so the prose shrinks by the header's length and the whole answer the voice receives stays under one bound; a source the ask wanted but nobody read is named there once, never again in the note. An empty findings list therefore never stands for a source that failed, was never configured or was never reached.

The allocator is two passes. The protected floor first: the header, the note and at least one whole finding line per source that returned a hit, clipped at a word boundary only when that last line cannot fit whole. Then a proportional fill that takes from the source furthest above its share of the room, so no single wide source crowds out the others. A clip never ends mid word, and the omitted count is the lines the read matched minus the lines the reply kept.

One research call answers the ask. The routed reads of every source run at once, a source that matched nothing gets exactly one broadened retry inside the same call (the query with its fillers dropped, never an authored operator, quoted phrase, sender, recipient, window or exclusion), and an ask that wants the content of a message and left one top hit has that mail body read in the same call, so the voice model never spends a round paging evidence the host can read itself.


C-LIVE additions. A source still reading counts as `still_reading` whichever path reads it, the web included (L8-06). Beside the header, a reply carries `sourceCoverage` rows only for a source whose gap the header cannot state (a deadline, a failed page, a page limit, an unknown or changing total): `examined`, `total`, `matches`, `represented`, `state`, `stop` and `more`, inside the same 2,500 character bound. The knowledge confidence line (`knowledge: confidence=...`) is a label under the finding head, never an item: it is not counted and no trim leaves it standing in for the hits, and memory the owner's ask did not name yields its lines before any source that answered beside it (L11-01). Memory never returns rows of the live call it runs in, by session id (L11-03), and a trim made after the header was built updates the header's count with the finding's. The live research call itself is admitted by the owner's turn; see [live-call.md](live-call.md#research-admission-and-the-bounded-operation).
